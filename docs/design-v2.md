## 0. 一句话

**RAG 保底；图谱只做三件事——关系召回、溯源、全局摘要。不追求全领域本体。**

## 1. 从文章里确认的四件事

| # | 观察 | 对我们的意义 |
|---|---|---|
| 1 | GraphRAG 的产出不是"一张大图"，而是 **lexical graph + entity graph + community** 三层 | 我们 v1 只有 chunk 层，实体层、社区层都缺；要分层设计而不是"要不要上图" |
| 2 | 作者明确提醒**必须换成 gpt-4o-mini 级的小模型**，否则成本暴增 | 抽取成本是可持续性的第一约束，必须先用小模型跑通再谈质量 |
| 3 | 实体带 `description`（一段文字画像），且回答引用的是 `[Data: Reports (33)]` 这种**社区报告** | 实体描述和社区摘要是真实产物，不是可选装饰 |
| 4 | 复杂问题上两个系统的短板都是"**语料连接度不够**"，不是算法不行 | 图的价值上限由语料决定；语料稀疏时上图就是白花钱 |

补充数据点：14 篇文章 → **380 节点 / 378 关系**；GraphRAG 索引管线有 15 个步骤（base_text_units → entities → community_reports → final_documents）。

## 2. v1 → v2 的改动（Δ）

| 项 | v1 | v2 | 理由 |
|---|---|---|---|
| 图结构 | 单一实体图（设想） | 三层：lexical / entity / community | 文章验证三层各司其职 |
| 查询 | 单路检索 | 三模式路由：local / global / drift | global 问题（"这批文章讲了什么"）纯向量检索答不了 |
| 溯源 | 文件 + 章节 | doc / chunk / 实体 / 社区报告 四级引用 | KG Builder 的核心优势就是可追溯 |
| schema | 人工拍板 | LLM 起草 + 问题清单校对 + 冻结版本 | 文章里用 Kimi 起草 Node Labels，命中率可用 |
| 评测 | 单跳问答 | 增加"跨主题综合""人物/机构画像""该拒答" | 文章暴露的短板正是跨簇泛化 |
| 成本 | 未建模 | 先 50 篇试跑，测 token/篇，设预算闸门 | 避免"索引一次吃掉一个月预算" |

## 3. 三层图的定义

| 层 | 节点 | 边 | 用途 | 是否必须 |
|---|---|---|---|---|
| lexical | Document、Chunk（含 embedding） | doc → chunk（含顺序、页码） | 检索、溯源 | **必须** |
| entity | Entity(type, name, description)、Relation | chunk → entity（MENTIONS + 证据句）、entity → entity（带置信度与时间） | 多跳召回、实体画像 | 看场景 |
| community | Community(id)、CommunityReport(summary) | entity → community（隶属） | 全局问题、主题综述 | 仅当需要全局问答 |

**关键：三层共用一套 doc_id / chunk_id**，否则引用对不上。

## 4. 抽取管线（含成本控制）

```
chunk ──① 实体+关系抽取（小模型，JSON Schema 约束）──→ 原始三元组（带证据句）
      ──② 实体归并（别名表 + embedding 聚类 + 人工队列）──→ 规范实体
      ──③ 实体描述生成（每实体一段 description，随文档增量更新）──→ 画像
      ──④ 社区检测（Leiden）+ 社区摘要（map-reduce）──→ 全局层
```

- **模型分层**：①②③④ 用小模型；最终答疑用强模型。
- **证据强制**：每个关系必须存 `evidence_chunk_id + 原文片段`，否则不可审计。
- **增量**：文档级 upsert；实体描述带 `updated_at` 与版本，冲突时保留新旧两版并标记。
- **闸门**：先跑 50 篇，测"每篇 token 数"与"实体重复率"，达标才全量。

## 5. 查询路由（三模式）

| 模式 | 触发 | 路径 | 输出 |
|---|---|---|---|
| local | 问题里有明确实体/专有名词 | 实体识别 → 邻域 1–2 跳 → 关联 chunk → 作答 | 带实体的引用 |
| global | 问题无具体实体，问整体（"讲了什么""有哪些主题"） | 选相关社区报告 → map-reduce 汇总 | 带社区报告引用 |
| drift | 具体细节 + 需要全局视角 | 先 local 拿细节，再引入社区上下文 | 混合引用 |

实现上先用规则 + 小分类器判定，不追求自动最优；判错的成本远低于过度设计。

## 6. 溯源契约（回答必须可点回）

每次回答附带：

```json
{
  "answer": "...",
  "citations": [
    {"doc_id": "...", "chunk_id": "...", "page": 3, "char_range": [120, 480],
     "quote": "原文片段", "entities": ["e_001"], "community_report": null}
  ]
}
```

前端：点引用 → 高亮原文；点实体 → 展开子图。**没有引用的答案视为失败**。

## 7. 评测（v2 补三类）

| 类型 | 例子 | 判定 |
|---|---|---|
| 单跳事实 | "住宿上限多少" | 答案 + 证据命中 |
| 跨主题综合 | "NAND/失效/可靠性三块怎么串起来" | 是否覆盖多簇证据（文章里两个系统都栽在这） |
| 人物/机构画像 | "介绍作者 X" | 档案类问题，考验实体描述与社区摘要 |
| 该拒答 | 语料里没有的问题 | 必须拒答，不许编 |

黄金集每条标"期望证据集合"，不只标最终答案。

## 8. 成本模型（估算，非实测）

假设：每篇 10 页、每页 800 字、500 字/chunk → 约 16 chunk/篇。

| 语料 | chunk 数 | 抽取输入 token（量级） | 说明 |
|---|---|---|---|
| 100 篇 | ~1.6k | ~1–2M | 单次全量，可接受 |
| 1,000 篇 | ~16k | ~10–20M | 需要预算闸门 |
| 10,000 篇 | ~160k | ~100–200M | 必须增量 + 分批，不能一次跑 |

（数量级估算，实际按模型单价与你语料的真实密度重算；社区摘要额外增加约 20–30%。）

需要改：

| 改动点 | 影响面 |

## 11. 与文章的差异（为什么我们不照抄）

| 文章做法 | 我们调整 | 原因 |
|---|---|---|
| GraphRAG 全家桶 | 先 lexical，entity 按需，community 待定 | 个人规模下全量索引性价比低 |
| Neo4j + APOC 本地部署 | 先 SQLite/PG 存三元组，图库后置 | 装配复杂度是主要成本，不是查询性能 |
| 用 GraphRAG 自带管线 | 自建薄管线，产物格式对齐三层图 | 避免被框架 DSL 锁死（ADR-0002） |
| gpt-4o-mini 全流程 | 抽取小模型、答疑强模型 | 同一策略，但按环节分档 |
